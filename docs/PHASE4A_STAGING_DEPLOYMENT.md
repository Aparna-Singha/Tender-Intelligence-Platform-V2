## Vercel to Cloudflare Access for laptop staging

For the current laptop staging path, publish the reviewed Tunnel hostname `api-staging.bidveda.space` only after the API is ready behind the intended Access application. Configure the Vercel project for `apps/web` with `NEXT_PUBLIC_API_URL=/api`, `API_PROXY_ORIGIN=https://api-staging.bidveda.space`, and the server-only `CF_ACCESS_CLIENT_ID` and `CF_ACCESS_CLIENT_SECRET` from the `bidveda-vercel-staging` service token. Store both credentials as Vercel sensitive environment variables for the intended staging environment; never use a `NEXT_PUBLIC_` prefix, log their values, or put them in a repository file. The production web environment rejects a missing origin or credentials. Keep the existing `NEXT_PUBLIC_STORAGE_ORIGIN` set to the R2 S3 API origin. The local direct-API development path remains available with an absolute `NEXT_PUBLIC_API_URL` and no proxy origin. The older VM/Caddy steps below are an alternative infrastructure plan; its API hostname must also be protected by a matching Access application before using this proxy. Do not send a service token to an unprotected public origin.

The Route Handler never forwards browser-supplied Access headers, forwarding headers, Host, Connection or Access cookies. It forwards only the application's session and CSRF cookies, preserves the browser `Origin` and `x-csrf-token` for the NestJS CSRF guard, and returns only approved application response headers and safe host-only cookies. Cloudflare's service token authenticates Vercel to Access; NestJS still authenticates the user and enforces tenant access. Unexpected upstream redirects and HTML Access challenges fail closed. All proxy responses use `Cache-Control: no-store`.

The handler streams request and response bodies without intentionally buffering them. [Vercel's documented Function payload limit](https://vercel.com/docs/functions/limitations) is 4.5 MB for request or response bodies; its duration depends on the plan and runtime settings. Large document bytes already use signed R2 PUT/GET URLs outside `/api`. Verify those browser flows and any remaining multipart or binary API route on staging. Do not assume streaming bypasses the request limit. Polling or SSE that exceeds the Function duration must reconnect or use the existing bounded polling path.

Before admitting users, verify the Tunnel hostname resolves only to the intended API and the Access Service Auth policy accepts the Vercel token. Deploy the reviewed Vercel build only after both server-only variables are set. From the deployed web origin, use synthetic accounts to check login, both Set-Cookie values, logout, invitation acceptance, CSRF rejection from a foreign origin, request IDs, two-tenant denials, signed R2 uploads/downloads and a deliberately unauthenticated API request. Confirm browser DevTools and Vercel logs never show Access credentials or a `CF_Authorization` cookie. Direct API requests without the Access service token must be denied at the Cloudflare boundary. The Tunnel hostname and Vercel frontend are not published in this repository change.

Caddy overwrites incoming `X-Forwarded-For` with the connecting peer address so an internet client cannot choose its rate-limit identity. Behind Vercel rewrites, that peer may be a shared Vercel egress address. The existing IP rate limits can therefore group unrelated users; quantify this on staging before a multi-user pilot. Do not trust a browser-supplied forwarding header to recover client IPs.

1. In Oracle Cloud, check current Always Free capacity in the selected home region before creating anything. Choose an Ampere A1 VM only if the account actually has capacity and quota. Reserve enough RAM for ClamAV signatures, PDF rendering, OCR, API, worker, Redis and the OS. Restrict SSH to named administrators; allow inbound TCP 80/443 only for the service, and deny public 4000, 4001, 3310 and 6379. Keep OS, Docker and container images patched. Configure disk and backup alerts. Do not select a paid shape or upgrade billing without separate approval.
2. Point `api.staging.example.test` at the VM. Caddy obtains and renews TLS certificates over 80/443. Check the certificate and DNS before setting `API_PROXY_ORIGIN`. Only Caddy publishes host ports; API, worker, Redis and ClamAV communicate on Docker networks. Keep the Caddy site name and `API_PROXY_ORIGIN` aligned.
3. Create a **disposable** Neon project or isolated branch in an approved region. Obtain a pooled TLS URL for runtime and a direct TLS URL for migration/restore operations. Put the pooled URL only in the VM secret store. The checked-in Prisma adapter caps each process at 10 connections, so API plus worker can request 20, excluding migration and operator sessions. Confirm Neon's actual endpoint limit before starting both containers; downsize/process-tune in a separate reviewed change if needed.
4. Create a **private** R2 Standard bucket and scoped S3 API token with only the staging bucket operations needed by the application. Keep the S3 endpoint in the form `https://<account-id>.r2.cloudflarestorage.com`, region `auto`, and path-style addressing. Presigned URLs use this S3 API hostname, **not** a public custom domain. Disable public access; do not use `r2.dev` as a document-serving path. [R2's S3 compatibility table](https://developers.cloudflare.com/r2/api/s3/api/) lists `HeadObject` and `CopyObject`, but the application's exact metadata and checksum sequence still requires live verification.
5. Configure R2 CORS for the exact Vercel staging origin: `PUT`, `GET`, `HEAD`; allow `content-type` and `x-amz-meta-sha256`; expose `ETag` if needed; use a short max age. A preview domain needs an explicit CORS entry or a controlled stable staging domain. Keep upload and download URL lifetimes at 300 and 60 seconds. Test a browser preflight, signed PUT with the SHA-256 metadata header, and `HeadObject` metadata before admitting users.
6. Configure a Vercel project for `apps/web` in this pnpm monorepo. Set `NEXT_PUBLIC_API_URL=/api`, `API_PROXY_ORIGIN` to the fixed HTTPS API origin, `CF_ACCESS_CLIENT_ID` and `CF_ACCESS_CLIENT_SECRET` as server-only values for the matching Access application, and `NEXT_PUBLIC_STORAGE_ORIGIN` to the R2 S3 API origin for the build. Use one stable HTTPS web domain for `WEB_APP_URL` and `WEB_ORIGIN` on the API. Do not put Access credentials, `DATABASE_URL`, R2 keys, Gemini keys, or API cookie secrets in `NEXT_PUBLIC_*` variables. Rebuild whenever the proxy or storage origin changes.
7. Provision a real transactional email service or separately deployed HTTPS adapter that accepts the API's `POST` JSON `{from, template, to, variables}` with a Bearer token and returns a successful HTTP status only after accepted delivery. Templates are `invitation` and `password_reset`. Set `EMAIL_DELIVERY_URL`, `EMAIL_DELIVERY_TOKEN`, and `EMAIL_FROM` together. ## Staging deployment and rollback

1. Review the commit, image digests, resource allocation and the [production environment template](../.env.production.example). Copy it to an **untracked** `.env.staging` on the VM, replace all sample values through the approved secret manager, limit file permissions to the deployment operator, and set `IMAGE_TAG` to the reviewed commit SHA. Do not print or archive this file in CI logs. `REDIS_URL` must contain the URL-encoded `REDIS_PASSWORD` and use host `redis`.
2. Build on the ARM64 VM or with a verified ARM64 builder. Run `docker compose --env-file .env.staging -f docker-compose.staging.yml config --quiet` and `docker compose --env-file .env.staging -f docker-compose.staging.yml build`. Do not promote untested `amd64` images to A1. The VM needs outbound HTTPS/DNS to Neon, R2, Gemini, mail delivery and ClamAV signature mirrors. The Docker `backend` network has no published ports but intentionally permits outbound connections.
3. Before application startup, take a Neon branch or restore point. Use the **direct** staging database URL in the operator shell for `pnpm --filter @tender/database db:migrate:deploy`, then verify `_prisma_migrations`, `SELECT extversion FROM pg_extension WHERE extname='vector'`, and a representative vector query. Never run `migrate dev` or `reset` against staging/production. If migration fails, stop release and restore the disposable branch or approved backup; do not improvise down-migrations of valid RAG retry history.
4. Start `redis` and `clamav` with `docker compose --env-file .env.staging -f docker-compose.staging.yml up -d --no-build redis clamav`, wait for health, then start `api`, `worker`, and `edge` with the same command and those service names. Check `https://api.staging.example.test/health`, `/ready`, worker `/ready` from inside its container, ClamAV PING and signature age, Redis AOF persistence and bounded JSON logs. The API `/ready` checks PostgreSQL, Redis and R2; worker readiness does not prove ClamAV signatures, so check scanner separately.
5. In Vercel preview, verify browser login, logout, forced session expiry, CSRF rejection from a foreign origin, authenticated reads/writes, upload, `EventSource`/progress or polling, and download. Confirm `tip_session` remains `HttpOnly; Secure; SameSite=Strict` and host-only on the web domain, no upstream URL or signed object URL leaks to logs, and no authenticated response is cached. Validate direct API requests from unrelated browser origins fail CORS/CSRF. The edge must reject untrusted forwarding headers and avoid exposing API port 4000.
6. Snapshot before every promotion. Keep the previous immutable application images and migration plan. For an application-only failure, redeploy previous images **only if the schema remains compatible**. For a schema or data failure, stop writers, restore a separately verified Neon branch/backup and matching images, then reconcile R2 objects and Redis jobs by authoritative PostgreSQL state. Redis AOF is a recovery aid, not the source of truth. Test recovery with synthetic data before using it operationally.

## Resource and plan constraints checked on 2026-10-22

- [Oracle Always Free documentation](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm) currently describes 1,500 A1 OCPU-hours and 9,000 GB-hours monthly, equivalent to about **2 OCPUs and 12 GB RAM** continuously; home-region capacity is not guaranteed, idle instances may be reclaimed, and volume/backup allowances are separate. This Compose allocation caps API at 1.5 GB, worker at 3 GB, Redis at 0.5 GB, ClamAV at 2.5 GB and Caddy at 128 MB, leaving headroom for OS, page cache and bursts. CPU caps are limits, not reserved capacity.
- [Vercel's Hobby terms](https://vercel.com/legal/terms) restrict that plan to personal or non-commercial use. Use a suitable paid/commercial plan before any commercial pilot. [Vercel Function limits](https://vercel.com/docs/functions/limitations) cap request and response payloads and vary by plan and runtime; usage, function and deployment limits may change.
- [Neon's current Free plan announcement](https://neon.com/blog/neon-free-plan-1-gb-per-project) describes 1 GB storage and 100 CU-hours per project monthly with a six-hour instant restore window. A continuously active queue-backed application may exceed compute allowances; check the live plan and regional limits before provisioning. Storage, connection limits, PITR and backup retention require explicit validation.
- [Cloudflare R2 pricing](https://developers.cloudflare.com/r2/pricing/) currently includes 10 GB-month Standard storage, 1 million Class A and 10 million Class B operations monthly; copies and uploads count as Class A, reads and HEAD count as Class B. Egress from R2 is listed as free, but storage/operation overages and other connected services can incur charges. [Presigned URLs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/) are bearer tokens and work only on the S3 API domain; [CORS](https://developers.cloudflare.com/r2/buckets/cors/) must be configured for browser use.
- [Gemini pricing and terms](https://ai.google.dev/gemini-api/docs/pricing) vary by model, quota and free/paid tier; free-tier data use may differ from paid. Explicitly approve data-handling terms and budget alerts before any live customer evidence is sent. Email delivery, domains, monitoring, outbound traffic and backup services can also cost money.
