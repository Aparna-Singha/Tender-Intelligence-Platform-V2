## Authority and data ownership

PostgreSQL owns tender versions, extraction fields, review decisions, assessments, conversations, answer runs, and citations. Private object storage owns binary copies. BullMQ carries work identifiers and cleanup keys. The API checks organisation scope, while the worker rechecks run and source freshness. The dashboard and evidence worker now use the same deadline selector. A field requires a valid source citation, a parseable date, and a usable finding and review state. A cited corrigendum outranks a primary document even when it shortens the deadline. The extraction model does not link a field to a specific corrigendum publication sequence, so different corrigendum dates remain unresolved unless an accepted review distinguishes one. When no source date is available, explicit tender metadata remains visible as metadata; a conflict does not silently fall back to it.

## Migration and recovery

`20261021000100_rag_retry_history` removes the unique question-message constraint, adds a nullable retry parent and indexes. Existing rows need no backfill. The previous application should not be deployed against a database containing multi-attempt questions because its retry code deletes history. Recovery should retain the expanded schema, restore the new application version, and replay queued retry jobs as needed. Re-adding the old unique constraint would require deleting valid retry history and is not an acceptable automatic rollback.

## Remaining validation

The synthetic unit tests cover authority, copy compensation, retry history and fallback labels. A database-backed migration test, live object-store failure test, browser workflow, and provider integration run are still needed before production readiness can be claimed. Failed immediate cleanup is retried through BullMQ; simultaneous failure of object storage and Redis still needs operational reconciliation of unreferenced objects.
